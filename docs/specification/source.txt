Project Specification: Custom Sports
Analytics Database & API
Prepared for: Independent Software Engineer / Contractor

Data Source Backend: Punting Form Public API V2 (Professional Tier)

Primary Filter Focus: Western Australian (WA) Racing (with initial emphasis on Saturday Ascot
Meetings)


  Architectural Core Directive: "Store Everything, Filter Later"
  The database must be built as a raw data warehouse. The ingestion pipeline must capture and
  store complete, unedited row payloads from the Punting Form API endpoints. Changing or
  adding filtering logic down the track must only require modifying the view/API layer, completely
  preserving the underlying data architecture.



1. Scope of Work & Target Deliverables

 • Daily ETL Ingestion Pipeline: An automated Python script running via cron job that
   authenticates against Punting Form V2 API, checks for target meetings (e.g., Saturday Ascot), and
   processes raw fields into a local warehouse.
 • Relational Database: A optimized PostgreSQL instance designed to map structured racing
   entities and rapidly index sequential fractional data.
 • Lightweight API Layer: A secure REST API built using FastAPI or Flask to expose modular,
   parameterised endpoints for automated form filtering.
 • Cross-Device User Interface: Responsive HTML table outputs or automated text webhooks
   (e.g., Telegram Bot) to allow secure remote access via any smartphone or computer.


2. Database Entity & Schema Requirements

The database schema must separate data into clean relational tables to handle sequential
parameters efficiently:

 • meetings : Tracks static daily parameters: Date, Track Name, Rail Position, Track Condition, and
   Moisture Variant.
 • races : Tracks Race Number, Distance, Class Grade, and Class Par values.
 • runners : Tracks Horse Name, Barrier, Weight, Trainer, Jockey, Predicted Settle ( PrSe ), Run
   Style ( RunStyle ), and Key Race Index ( KRI ).

4. Custom Algorithmic Filtering Rules

The developer must write modular endpoints that allow dynamic parameter passing. The core filters
required for day-one deployment include:

A. The Automated Class Dropper & Hot Form Scanner
Isolates runners stepping down significantly in competitive grade who competed in high-pressure
historical fields.

C. Custom Dynamic Trainer Strike Rates
The system must query historical warehouse entries to aggregate custom trainer trends dynamically
based on current parameters:

 • 1st-Up Pattern: Group by Trainer where RB == 0 to evaluate fresh-up success percentages.
 • The 7-Day Backup: Group by Trainer where DLR <= 7 to expose trainers with high ROI when
   running horses on tight backup schedules.
